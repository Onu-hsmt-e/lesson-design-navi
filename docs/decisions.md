# 設計判断の記録(decisions)

形式: 日付 / 判断 / 理由 / 検討した他の案。タスクを終えるたびに、ここへ一言書き足します。

## 設計書との意図的な差異

### D-1 保存先をサーバーのPostgreSQLにする
- 日付: 2026-11-04
- 判断: 授業データは、サーバーのPostgreSQLに保存する。
- 理由: 設計書は「利用者個人持ち(手元のファイルが正本)」だが、このリポジトリは公開デモとして動かすため、サーバー側の保存が必要。
- 他の案: 手元のファイルを正本にする(デモが成り立たない)。
- 補足: 余力があれば、確定データのJSON書き出し・読み込みを付けて、設計書の方針に寄せる。

### D-2 保存するのは自作・架空のサンプルだけ。30日で削除する
- 日付: 2026-11-04
- 判断: 保存は自作・架空のサンプルに限る。保存期限は30日。利用者が自分で全データを消せる。
- 理由: 設計書は、自作プリントの本文を保存してよいかを「要決定」にしている。決まるまでは、保存するデータを最小にする。
- 他の案: 期限なしで保存する(扱うデータの範囲が広がる)。
- 補足: 注意書きは、入力画面ではなく利用条件のページに書く(設計書の10/21の決定)。デモ画面には「サンプルデータ専用」の帯を出す。

### D-3 手法はサーバー側のルールで決め、AIは特徴の抽出と理由文だけを担当する
- 日付: 2026-11-04
- 判断: 活動の特徴(複数解法・基本範囲内・つまずきやすい・役割分担)をAIが抽出し、手法は決まった順序のコードで決める。
- 理由: 設計書は判断ロジックをサーバー側に置くとしている。同じ入力なら同じ結果になり、テストで固定できる。AIが誤っても、影響が特徴の抽出と理由文に限られる。
- 他の案: AIに手法まで決めさせる(結果が揺れ、テストで固定できない)。

### D-4 入力は貼り付けテキストだけにする
- 日付: 2026-11-04
- 判断: 画像・PDFの取り込みは作らない。
- 理由: 取り込み(OCR)は、それだけで大きな機能になる。ポートフォリオでは、設計から印刷までの1本の流れを優先する。

## 技術の選択

### T-1 構成は、React(Vite)+ Fastify + PostgreSQL + Prisma の分離型
- 日付: 2026-11
- 判断: web と api を別のアプリにし、pnpm workspace で束ねる。型とスキーマは `packages/shared` で共有する。
- 理由: フロントのコンポーネント設計と、バックエンドの設計判断を、それぞれ説明できる形で残すため。
- 他の案: Next.jsの一体型(設計判断が見えにくい)、BaaS(バックエンドを書いた証拠が残らない)。

### T-2 ORMにPrismaを使う
- 日付: 2026-11
- 判断: Prismaでスキーマとマイグレーションを管理する。
- 理由: スキーマ設計とマイグレーションの履歴を、リポジトリに残せる。型が生成される。
- 他の案: 生のSQLと手書きの型(自由度は高いが、書く量が増える)。

## 2-2 スキーマの判断

- enum にした理由: schoolLevel・method・priority などは取りうる値が決まっている。DB が不正な値を拒否し、TypeScript の型としても使えるため。値は英語名にし、画面の日本語は packages/shared で対応づける。
- Json にした列: practiceSettings、features、payload。項目が増減しやすく、DB 側で検索しないため。中身は zod で検証する。
- インデックス: userId、lessonId、expiresAt に付けた。一覧表示と期限切れ削除で絞り込む列だから。
- Session.id だけ cuid ではなく、トークンのハッシュを入れる。
- Suggestion.where は Prisma の where と紛らわしいので place にした。
- UsageLog は (userId, date) を一意にし、1日1行に加算する。
